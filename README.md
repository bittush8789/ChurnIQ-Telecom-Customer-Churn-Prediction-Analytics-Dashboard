# 📡 ChurnIQ — Telecom Customer Churn Prediction & Analytics Dashboard

An end-to-end machine-learning demo that predicts whether a telecom customer is
likely to churn and turns the prediction into retention insight.

Built with **Python, Streamlit, Pandas, NumPy, scikit-learn, XGBoost, Plotly and
Joblib**.

> ⚠️ **Synthetic data notice**
> Every customer record in this project is **randomly generated**. The dataset is
> labelled as synthetic everywhere it appears. Model metrics and predictions are
> for demonstration and learning only — they are **not** real telecom business
> performance and must not be used for real decisions.

---

## ✨ What the app does

| Section | What you can do |
|---|---|
| **Dashboard Overview** | See total / active / churned customers, churn rate, and the number of high-risk customers. Explore churn by contract, tenure, payment method and monthly charges. |
| **Customer Analytics** | Filter the portfolio by contract, internet service and gender. Inspect churn distributions, tenure bands, billing behaviour and a contract × internet churn heatmap. |
| **Model Performance** | Compare Logistic Regression, Decision Tree, Random Forest and XGBoost. Review 5-fold cross-validation results, test metrics, confusion matrix, ROC curve and feature importance. |
| **Churn Prediction** | Enter a customer profile to get a churn probability, Yes/No status and High/Medium/Low risk band. |
| **Retention Insights** | Review a selected high-risk customer. ML risk is shown **separately** from deterministic rule-based recommendations. Download the full high-risk list. |

The sidebar also shows model status and lets you **retrain all models** in one
click.

## 🚀 Installation and run

### 1. Create a virtual environment (recommended)

**Windows (PowerShell):**

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

**macOS / Linux:**

```bash
python -m venv .venv
source .venv/bin/activate
```

### 2. Install dependencies

```bash
pip install -r requirements.txt
```

### 3. Run the dashboard

```bash
streamlit run app.py
```

Open the URL shown in the terminal (usually `http://localhost:8501`).

On the **first run**, the app automatically:

1. Generates 7,000 synthetic customers into `artifacts/telecom_churn_synthetic.csv`.
2. Trains and compares four models with 5-fold stratified cross-validation.
3. Saves the best pipeline to `artifacts/churn_model.joblib`.
4. Starts the dashboard.

Later runs load the saved artifacts instantly. Use **Retrain all models** in the
sidebar to rebuild them.

## 🗂️ Synthetic dataset

Generated by `data_generator.py` with `numpy.random.default_rng(42)` and 7,000
records.

| Feature | Type | Description |
|---|---|---|
| `CustomerID` | ID | Unique synthetic customer identifier (`TC-000001` …) |
| `Gender` | Categorical | Female / Male |
| `SeniorCitizen` | Binary | 1 = senior citizen, 0 = not |
| `Tenure` | Numeric | Months with the company (0–72) |
| `ContractType` | Categorical | Month-to-month / One year / Two year |
| `MonthlyCharges` | Numeric | Current monthly bill ($) |
| `TotalCharges` | Numeric | Lifetime charges ($) |
| `InternetService` | Categorical | DSL / Fiber optic / No |
| `PhoneService` | Categorical | Yes / No |
| `MultipleLines` | Categorical | Yes / No / No phone service |
| `OnlineSecurity` | Categorical | Yes / No / No internet service |
| `TechSupport` | Categorical | Yes / No / No internet service |
| `PaymentMethod` | Categorical | Electronic check / Mailed check / Bank transfer / Credit card |
| `PaperlessBilling` | Categorical | Yes / No |
| `MonthlyUsage` | Numeric | Estimated monthly data usage (GB) |
| `CustomerSupportCalls` | Numeric | Support contacts in the last six months |
| `Churn` | Target | Yes / No |

### How churn was simulated

Churn probability is generated from a logistic function with realistic drivers:

- **Higher churn:** month-to-month contracts, short tenure, fiber optic service,
  no online security, no tech support, electronic-check payment, paperless
  billing, senior citizens, higher bills, more support calls.
- **Lower churn:** two-year contracts, long tenure, no internet service, lower
  bills.

Random noise is added so the problem is not perfectly separable. The resulting
churn rate is approximately **29%**.

A small amount of missing data is injected into `TotalCharges`, `MonthlyUsage`,
`PaymentMethod` and `CustomerSupportCalls` to exercise imputation.

## 🤖 Machine-learning workflow

1. **Generate** the synthetic dataset (`data_generator.py`).
2. **Clean** the data: coerce `TotalCharges` to numeric, de-duplicate customers,
   remove rows without a valid target.
3. **Split** 80% train / 20% test with `train_test_split(..., stratify=y,
   random_state=42)`.
4. **Preprocess inside a pipeline** (`ColumnTransformer`):
   - Numeric: median imputation → `StandardScaler`
   - Categorical: most-frequent imputation → `OneHotEncoder(handle_unknown="ignore")`
5. **Cross-validate** four candidate models on the training set only:
   - Logistic Regression
   - Decision Tree
   - Random Forest
   - XGBoost
6. Use **5-fold `StratifiedKFold`** with shuffle and `random_state=42`.
7. **Select** the model with the highest mean validation **F1-score**.
8. **Refit** the winning pipeline on the full training set.
9. **Evaluate once** on the untouched test set: accuracy, precision, recall,
   F1-score and ROC-AUC, plus confusion matrix and ROC curve.
10. **Persist** the fitted pipeline with Joblib.

### Why there is no data leakage

- Imputers, scalers and encoders live **inside** the scikit-learn `Pipeline`.
- Cross-validation refits the entire pipeline on each training fold, so
  validation folds never influence preprocessing.
- The test set is used **only once**, after model selection.
- The saved artifact is the complete pipeline (preprocessing + model), so the
  dashboard cannot accidentally preprocess differently.

|---|---|---|

## 🧠 Prediction and risk bands

The saved pipeline predicts `P(churn = Yes)`. The dashboard uses:

| Risk level | Probability |
|---|---|
| **High** | ≥ 60% |
| **Medium** | 30% – 60% |
| **Low** | < 30% |

The **Yes/No** status uses a 50% decision threshold. These thresholds are
business choices and can be tuned in `ml_pipeline.py`.

Input validation rejects missing fields, non-numeric values and out-of-range
numbers. Service-dependent fields are normalised automatically (for example, no
internet service becomes “No internet service”).

## 🧾 Rule-based recommendations vs ML predictions

These are deliberately separate:

- **ML assessment** — a statistical probability learned from synthetic
  historical patterns. It ranks risk but does not explain cause.
- **Rule-based recommendations** — transparent, deterministic business rules
  such as:
  - Month-to-month contract → offer a better contract plan.
  - 4+ support calls → assign proactive customer support.
  - Tenure ≤ 12 months → strengthen onboarding.
  - Monthly charges ≥ $85 → review pricing concerns.
  - No security/tech support → bundle support services.
  - Electronic check → incentivise automatic payments.
  - Tenure ≥ 48 months → offer a loyalty discount.

The UI labels which signal is which. The rule engine never uses the model score.

## 🛠️ Troubleshooting

**`ModuleNotFoundError`** — activate the virtual environment and run
`pip install -r requirements.txt` again.

**Port already in use** — run `streamlit run app.py --server.port 8502`.

**Training feels slow on first run** — the app trains four models with 5-fold
cross-validation. On a typical laptop this takes roughly 15–45 seconds. Later
runs use the saved model.

**Corrupt or incompatible model file** — delete `artifacts/churn_model.joblib`
or click **Retrain all models**. The app automatically retrains if the artifact
cannot be loaded.

**XGBoost is unavailable** — `ml_pipeline.py` skips XGBoost gracefully and
compares the remaining three models. Install it with `pip install xgboost` to
restore the full comparison.

## 📌 Limitations

- Synthetic data cannot reproduce the complexity of real customer behaviour.
- The model is not calibrated for production decisions and has no fairness,
  drift or uplift evaluation.
- Rule-based recommendations are illustrative heuristics, not proven
  interventions.
- Metrics should never be presented as real telecom business results.
